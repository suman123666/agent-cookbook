# 第 8 章 · 评估与可观测 · 知识要点

## 本章定位

前 7 章学会"做 agent"。本章学**科学地说"我的 agent 比上一版好 15%"**。
是 agent 从「能跑」推到「可量化」的工程分水岭。

---

# 🎯 为什么评估这么重要

```
业余做法：跑两次 → "感觉变好了"
专业做法：跑 50 个评估集 case → 量化 → "成功率 73% → 81%"
```

**"感觉变好"不算数的 6 个原因**：

```
① 样本太小（N=1-2 统计上没意义）
② 确认偏误（你的大脑会"印证自己的期望"）
③ 跷跷板效应（A 变好但 B、C 变差）
④ 无基线（无法对比）
⑤ 不可复现（主观判断会变）
⑥ 不可沟通（推不动业务决策）
```

→ 评估的本质是「科学方法」：可量化、可复现、可对比。

---

# 🏗 评估三层（核心架构）

| 层 | 关注 | 对应传统测试 |
|----|------|------------|
| **Unit Eval** | 单步对错（工具选择 / 参数 / 召回质量） | 单元测试 |
| **E2E Eval** | 整体任务完成情况 | 集成/E2E 测试 |
| **Online Eval** | 真实用户的表现 | 生产监控 + 用户反馈 |

**关键差异**：
- 传统测试是 deterministic（assert == ）
- agent 评估是 probabilistic（跑 100 次看统计成功率）

---

# 📊 4 大主流指标

```
1. 成功率（Success Rate）       —— 最核心
2. 工具使用准确率（Tool Accuracy）
3. 平均轮数（Avg Turns）         —— 效率
4. 成本/任务（Cost per Task）     —— 经济性
```

**好指标特征**：可量化、可对比、有方向（越大或越小越好明确）。

---

# 📋 评估数据集（最被忽视也最重要）

**评估集 = 考题**。没好考题谈不上"做得好"。

## 三种来源

```
1. 历史日志（最真实）★    从生产 trace 挑代表性 case
2. 人工编写（最可控）      工程师/PM 写黄金问答
3. LLM 生成（最快）        批量生成测试用例

实战通常组合：30% 历史 + 50% 人工 + 20% LLM 生成
```

## 黄金答案三类型（不同视角的叫法都见过，都指同一回事）

```
精确匹配 / 精确型 (Exact)        数学/有 deterministic 答案    → 规则评分
结构化匹配 / 结构化型 (Structured) "应调哪些工具、传什么参数"   → 规则评分
模糊匹配 / 参考型 (Fuzzy/Reference) 开放回答                    → LLM-as-judge
```

视角差异：「模糊匹配」从评分方式角度命名（匹配方式是模糊的）；
「参考型」从黄金答案本身角度命名（答案是参考性的）。本质同一组三类。

---

# ⚖️ 三种评分方式

| 方式 | 优 | 缺 | 用于 |
|------|-----|-----|------|
| 规则评分 ★首选 | 快、可复现、便宜 | 开放回答没法用 | 工具调用 / 结构化输出 |
| LLM-as-judge | 能评开放回答 | 有偏差、贵、不稳 | 答案质量 / 对话评估 |
| 人工评分 | 最准 | 慢、贵、不可扩展 | 抽样校验 |

**实战混合**：能用规则就规则 → 剩下用 LLM-judge → 5% 抽人核校验。

---

# ⚠️ LLM-as-judge 的 4 大偏差

```
1. 位置偏差    先呈现的答案被偏爱
2. 长度偏差    长答案被偏爱（看起来更详细）
3. 自我偏好    模型偏爱自己生成的内容
4. 不稳定      同输入多次得分不同
```

**4 个缓解**：
- 位置随机化（多次评+随机顺序）
- 评分维度明确（不问"哪个好"，问"按 X/Y/Z 维度 1-5 分"）
- 用更强模型评（Opus 评 Haiku 输出）
- 多轮平均 / 多模型平均

---

# 🎯 成功率定义的 4 种模式

```
A. 严格 AND     所有维度都过 = 成功（最严苛，暴露每个缺陷）
B. 加权分数     按权重加和（灵活，权重靠拍脑袋）
C. 分级评分     0-1 连续分（信息丰富，要细心设计）
D. 业务指标     用户满意度/转化率（终极标准，需上线数据）
```

**「合取陷阱」**：多维度 AND，每个 80% 通过 → 整体 0.8³ = 51.2%！这不是 bug 是数学。

**铁律**：**定义一旦选定就不要改**——否则纵向对比无意义。

# 🔄 多轮对话评估（进阶）

## 三种策略

```
① 固定脚本    预设 user 每句话，agent 依次响应
              ✅ 可复现 ❌ 不真实
              
② 模拟用户    用 LLM 扮演 user 跟 agent 对话
              ✅ 动态覆盖广 ❌ 贵
              
③ 录制回放    从生产日志回放真实对话
              ✅ 最真实 ❌ 需要线上数据
```

## 多轮特有的 5 大失败模式

```
1. 遗忘     前面说过的，后面忘了
2. 矛盾     前后自相矛盾
3. 循环     一直问同一个问题
4. 早退     用户没说完就总结结束
5. 越界     超出用户需求做事
```

## 多轮综合指标

```
任务完成率 / 完成轮数 / 首次解决率 / 会话保持度 / 一致性 / 用户体验分
```

注意 **LLM-judge 在多轮里偏差被放大**，必须多次取平均。

---

# 📅 评估时机（决定一切）

```
开发期      每改一次 → 跑评估 → 看 regression
            ← 这是最被忽视的，大多数人等"做完"才评估

发布前      跑完整评估集 + 人工抽样 → 达标才上线

上线后      在线指标监控 + 定期抽样跑评估集
```

**核心铁律**：评估集应在开发第一天就有的，不是"做完再评"。

# 📦 实战：本地评估脚本

文件：`chapter_08_evaluation/eval_rag_agent.py`

评估对象：第 5 章的 RAG agent。

## 关键设计

```python
DATASET = [
    {"id": "knowledge_1", "input": ..., "should_search": True, "expected_keywords": [...]},
    {"id": "chitchat_1",  "input": ..., "should_search": False, "expected_keywords": []},
    # 4 正例 + 2 反例 ← 必须有反例（否则全调工具都"过"）
]

# 三层评估同时跑
tool_correct = (used_search == should_search)            # Unit
answer_quality = keywords_hit >= half                    # E2E
rounds = len(loops)                                       # 效率指标

# 严格 AND 定义成功率
both_correct = tool_correct and answer_quality
```

## 输出

```
工具使用准确率: 6/6 = 100.0%
答案质量通过率: 5/6 =  83.3%
整体成功率:    5/6 =  83.3%   ★ 综合指标
平均轮数:      2.8
失败 case 列表 + 失败原因
```

**这就是基线**——下次改完 prompt 再跑，数字直接对比。

# 📌 关键心智沉淀

```
1. 评估是工程化的「分水岭」——不评估就只能"感觉"
2. 评估集 = 考题，必须涵盖正反例
3. 三种评分方式按场景搭配，不是二选一
4. LLM-as-judge 必要但要警惕偏差
5. 成功率定义一旦定就别动（否则无法纵向对比）
6. 多轮评估比单轮难 5-10 倍，第 10 章如果做多轮 agent 再实践
```
