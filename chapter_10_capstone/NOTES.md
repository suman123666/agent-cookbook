# 🏗 设计决策（你亲手做的）

## 业务设计

```
方向选择：业务人员问数 agent（vs 数据人员副驾驶）
聚焦人群：电商运营小李
关键切片：达人/直播带货效果分析
评估口径：宽松口径（业内标准）
归因方式：末次点击（业内主流）
性价比定义：(GMV × (1-退货率)) / 投放费
```

## 数据设计

```
5 张表：influencers / campaigns / orders / skus / refunds
时间跨度：6 个月（2025-12 ~ 2026-06，含 618 期间）
数据规模：150 主播 / 80 SKU / 1545 投放 / 30000 订单 / 1787 退货
平台范围：抖音 / 小红书 / 快手
主播垂类：美妆（主） + 时尚 / 母婴 / 美食 / 数码
SKU 品类：口红 / 精华 / 面膜 / 眼影 / 香水
```

## Agent 设计

```
工具清单（5 个）：
  lookup_schema(table)    查表结构
  lookup_metric(term)     查业务术语（语义层 RAG）★ 关键
  execute_sql(query)      执行 SQL（只读 + 限 1000 行）
  plot_chart(data, type)  生成图表
  ask_user(question)      反问澄清 ★ 安全兜底

决策流程：
  懂吗 → 查术语 → 查表 → 写 SQL → 反思 → (重试 / 答复)

错误处理：
  retry 上限 3 次
  单独 Reflect + 同模型（客观 + 便宜）
  Reflect 3 次过不了 → 老实承认 / ask_user 兜底
```

# 💡 项目过程中暴露的 6 个真实问题（教学价值最高）

## ① 数据真实性陷阱（投放费用造太高）

```
第一次造数据：整体 ROI 0.31（远低于真实 1.5-5）
诊断：把头部主播费用造到 5-20 万/次，实际真实区间是 1.5-6 万
修复：投放费用整体降 60%
教训：合成数据看似简单，参数调不准就废了
```

## ② NL2SQL 经典坑：JOIN 重复计数

```
LLM 第一次写：SUM(orders.amount) / SUM(campaigns.cost) 直接 JOIN
陷阱：一次 campaign 多个订单 → cost 被重复加 N 次 → 分母虚高
修复：sql_template 强制用 CTE 分开算分子分母
教训：业务公式 + SQL 套路必须标准化
```

## ③ 业务口径冲突（严格 vs 宽松）

```
LLM 严格口径：本周费用 vs 本周内的订单 → ROI 0.42
inspect 宽松口径：本周费用 vs 本周所有达人订单 → ROI 1.87
两者都对，但口径不统一时数字差 4 倍
解决：sql_template 明确锁定为「宽松口径」（公司统一）
教训：指标定义统一比 SQL 写法更重要
```

## ④ 时间词被 LLM 自由解读

```
metrics_dict 写"最近一周 = 5-27 ~ 6-03"
LLM 自己写了 5-27 ~ 6-02（少 6-03）
修复：system prompt 加铁律「时间词必查 lookup_metric」
教训：哪怕看起来"简单"的概念，也要强制规范化
```

## ⑤ Reflect 过度自信

```
system prompt 写"ROI > 10 异常"
Reflect LLM 自己延伸："ROI < 1 也异常"
实际数据 ROI 1.8 → 被误判异常 → 重试 3 次
修复：Reflect prompt 加"默认放行原则 + 保守判定"
教训：质量门卫要"刚刚好"严格，过严过松都翻车
```

## ⑥ Agent 稳定性（同 prompt 不同结果）

```
q6 单独跑：完美通过
q6 评估时跑：触发兜底 ask_user
原因：LLM 即使 temperature=0 也有微小不确定性
业内做法：N 次评估取平均、降低 LLM 自由度、majority vote
教训：单 agent 跑通 ≠ 稳定可用，要量化"通过率"而不是"通过"
```

# 🎓 关键产品洞察（带走的真东西）

```
1. 「语义层」不是术语字典，是「经过验证的 SQL 模板库」
   → 生产级问数 agent 的核心壁垒

2. 「口径会议」比「指标公式」更重要
   → 数据团队的真正价值是统一口径

3. Reflect 是 agent 安全的关键，但需要持续调优
   → 太严杀好结果，太松放过错结果

4. ask_user 是「优雅失败」的必备机制
   → 比瞎编答案好 10 倍

5. agent 稳定性 = 「单次准确率 × 多次一致性」
   → 上线前要量化两个，不能只看单次

6. 数据合成本身是个产品 —— 参数调不准就废
   → 验证、迭代、再验证

7. NL2SQL 的真难点不是 SQL 语法
   → 是业务公式标准化 + 工程师 SQL 经验封装
```
